# ADR-0012: Identity and authentication

Status: **Proposed** · 2026-10-15. Not Accepted. No M1 code starts until the owner marks this Accepted.

Owner decisions recorded so far (2026-10-15; they do not change the status): drop `@node-rs/argon2` and use `node:crypto` `argon2`; breached-password list candidate A (NCSC top 100k); adopt ASVS 5.0.0; password minimum 15 with no composition rules; the API-key layout exception with its conditions; the signup tenant-id fix; the three ADR-0007 amendments (in ADR-0013).

## Context

M1 needs sign-up, passwords, MFA, sessions, RBAC and API keys on top of the tenancy model in ADR-0007. The ADR index has reserved this decision as "identity provider build-vs-embed (M1)". Constraints that shape it:

- Tenant isolation is absolute (principle 4). Identity data has to fit RLS, composite foreign keys and the audit log.
- Everything runs locally and self-hosted; no paid or managed service is approved (CLAUDE.md).
- Security-critical code that we write ourselves is a liability, so the design should be mostly glue between vetted primitives.
- OIDC and WebAuthn are deferred past the M1 gate (owner, 2026-10-15). SAML and SCIM are M11.

## Decision

**Build a thin identity layer in-house, on vetted primitives.** We write the data model, the flows and the authorization checks. We write none of the cryptography and define no token formats beyond one identifier layout (below).

### Explicitly NOT built

- **No custom cryptography.** No home-made cipher, mode, KDF, hash, MAC, nonce scheme or key-wrap format. AES-256-GCM and Argon2id come from a vetted implementation. Our code only chooses parameters, supplies AAD and stores outputs.
- **No custom token formats.**
  - Sessions are opaque random strings. There are **no JWTs, no signed or encrypted cookies**, and no self-describing claims.
  - The server trusts nothing it parses out of a token. Every token is looked up by its hash.
- **The single exception is the API key layout** `prysm_<tenant>_<key_id>_<secret>` (owner-approved 2026-10-15 with conditions). It is a fixed `prysm_` prefix plus three opaque identifiers, with no claims, signature or checksum. Conditions:
  1. The fixed `prysm_` prefix stays, so secret scanners can find leaked keys.
  2. The `<tenant>` part is **untrusted input until the hash compare succeeds.** It is used only to choose which tenant scope to look in.
  3. Lookup order is fixed: split the key, then `withTenant(<tenant>)`, then select by `key_id` under RLS, then a **constant-time** compare of the hash. Failure at any step returns the same generic error.
  4. Keys are **never logged**, never placed in URLs or query strings, never written to traces or error bodies. They travel in a header only. Canary tests cover logs, traces and errors.
- No home-grown TOTP, no custom OTP delivery, no SMS or email codes as a second factor.
- No identity provider, OAuth/OIDC server, or SSO in M1. No WebAuthn in M1.
- No composition rules for passwords beyond length and the offline lists.
- No `SECURITY DEFINER` functions and no RLS bypass anywhere in identity code (owner, 2026-10-15).
- No secrets in logs, traces or error bodies; the existing canary tests are extended to cover them.

### Password hashing policy

- **Primitive:** `node:crypto` `argon2('argon2id', …)` (async form on the request path). Added in Node v24.7.0; the repo requires Node 24.14 or newer. In the Node v24.21.0 documentation it carries no per-API stability marker and sits under the crypto module's "Stability: 2 - Stable". That is the documented state, not a guarantee, so the checks below are permanent.
- **Stored per password:** algorithm, memory (KiB), passes, parallelism, a 16-byte random salt, and the 32-byte tag, each in its own column. No PHC string format, so no parser to write.
- **Starting parameters:** the OWASP minimum (19 MiB, 2 passes, parallelism 1) as a floor; PR 6 tunes upward on the reference machine and records the measurement. A password verify takes roughly 25 ms at the floor on the developer host.
- **Rehash on login:** after a successful verify, if the stored algorithm or any parameter is below the current policy, the password is hashed again with the current parameters and the row is updated in the same request. The policy lives in one constant in `packages/crypto`; raising it needs a code change and a test update. Because there is no `needsRehash` helper, a unit test pins the comparison logic (stored below policy, equal, above policy).
- **Boot check:** the api refuses to start if `typeof crypto.argon2 !== 'function'`, and logs only that fact.
- **Permanent test vector:** the RFC 9106 Argon2id test vector runs in CI on every build, as a unit test in `packages/crypto`. A Node upgrade that changes the output fails the build.
- **Concurrency limit (memory-DoS reasoning):** one hash allocates the configured memory (19 MiB at the floor) and keeps a worker thread busy. Node runs async KDF work on the libuv thread pool, which has 4 threads by default, so a burst of logins queues rather than runs in parallel, but each in-flight hash still pins its memory and a long queue delays every other pool user (DNS, file I/O). So hashing goes through a bounded semaphore (default: 4 in flight, a small bounded queue; extra requests get a generic 429 or 503 before any hashing starts). Rate limits run before the semaphore. A test floods the endpoint and asserts bounded memory growth and that unrelated requests still answer.
- **No pepper in M1.** Node's `secret` parameter is available if we add one later (M11 hardening).

### Data and flow in brief

- Global tables (no RLS, allowlisted and tested, see ADR-0013): `users`, `user_mfa_factors`, `mfa_recovery_codes`, `sessions`, `auth_events`. Tenant tables follow ADR-0007, including `memberships`, `api_keys`, `admin_audit_log`.
- A new session is `mfa_pending` and may call only MFA enrol/verify. MFA is mandatory for every account. **Password reset never bypasses MFA.** A lost second factor is recovered only with a recovery code or an Owner-initiated, audited reset.
- Sessions: 30 min idle, 12 h absolute, rotated on login, MFA success, tenant change and privilege change. Stored in Postgres. Users can list and end their own sessions; admins can end any session in their tenant; disabling an account ends all its sessions; changing a credential offers to end the others.
- Changing the email address or MFA settings requires fresh authentication.
- RBAC: six roles, a permission map in `core-types`, and an exhaustive role × permission test.

**V6.5.5 note (verbatim from ASVS 5.0.0, CC BY-SA 4.0, OWASP Foundation):** "Verify that out-of-band authentication requests, codes, or tokens, as well as time-based one-time passwords (TOTPs) have a defined lifetime. Out of band requests must have a maximum lifetime of 10 minutes and for TOTP a maximum lifetime of 30 seconds." (L2 and L3.)

- **Does it require a current-step-only window? No, not explicitly.** The text sets a maximum lifetime of 30 seconds and says nothing about clock drift or adjacent steps. The chapter text and the CSV carry no further guidance on windows. A standard 30 s TOTP step satisfies it, and RFC 6238 itself discusses accepting a neighbouring step to cover clock drift and network delay.
- **Decision (per the owner's rule):** TOTP uses a 30 s step with a **±1 step tolerance** (previous, current and next), so valid codes do not fail at step boundaries. Each accepted code is single-use through `last_used_step` (V6.5.1), and the verify endpoint is rate limited.
- **Tradeoff, stated plainly:** with a ±1 tolerance a code can be accepted for up to about 90 seconds from the start of the previous step's validity, which is longer than 30 seconds on a strict reading. An assessor could read V6.5.5 that way. Single use, rate limiting and the 6-digit space make guessing impractical, but this is an interpretation, not a clear pass.
- **Fallback:** the tolerance is one constant (`TOTP_STEP_TOLERANCE`, default 1). Setting it to 0 gives the strict reading at the cost of more failed logins near step boundaries. We revisit it at the M11 ASVS sign-off.

**Design changes forced by checking the real text** (all already reflected above; none was in the first draft):

1. V6.5.5 forced a closer reading of the TOTP window; the result is the ±1 step tolerance with single use described in the V6.5.5 note below.
2. Recovery codes are 128-bit and hashed with SHA-256, not 80-bit. V6.5.2 and V11.5.1 only allow a standard hash from 112 bits and ask for 128.
3. Password reset must not bypass MFA (V6.4.3), and a lost factor needs identity proofing (V6.4.4).
4. Session management gains list-and-end-sessions, admin termination, end-on-disable, end-others-after-credential-change and re-authentication for sensitive changes (V7.4.x, V7.5.x). These add scope to PRs 6, 7 and 11.
5. A key-management policy and a crypto inventory document are needed (V11.1.1, V11.1.2).
6. V13.3.1 (secrets in a key vault) is only partly met until cloud KMS arrives in M11.

## Breached-password list

- **Choice (owner, 2026-10-15): candidate A, the UK NCSC top 100,000 list.** Nothing is added until PR 6. When it is added: re-fetch the file, record its SHA-256 and retrieval date, re-read the NCSC terms, and add the OGL v3.0 attribution to `NOTICE` in that PR.
- **Provenance question, recorded and not assumed away:** the NCSC site terms license its content under the Open Government Licence v3.0 but exclude material the NCSC holds under third-party licence. I could not establish from the NCSC pages how this list was compiled or whether it derives from third-party breach data. Before the file is added, the PR must either find an NCSC statement covering the file or record the residual licensing risk for the owner to accept. The decision to ship is then the owner's.
- **Limit, stated honestly:** 100,000 passwords is a weak breach corpus compared with the hundreds of millions in large breach sets. It satisfies the letter of V6.2.4 (the top 3000) and gives a basic V6.2.12 check, but it will miss most real breached passwords. This is acceptable for M1 and is to be revisited (a larger offline corpus or a checked hash set) before the M11 ASVS sign-off.
- Rejected: candidate C (Probable-Wordlists, CC BY-SA 4.0 share-alike beside Apache-2.0). Candidate B (Xato slice, MIT repo licence) stays a fallback if A's provenance cannot be settled.

## Dependencies

Packages this ADR relies on are listed with versions, release dates, licences and install-script status in the M1 plan, §12. Owner decisions on 2026-10-15:

- Approved: `otpauth`, `@fastify/cookie`, `@fastify/helmet`, `@fastify/rate-limit`, `fastify-type-provider-zod` (with its `openapi-types` peer), `@fastify/swagger`, `@playwright/test`, and `@axe-core/playwright` (MPL-2.0, dev only).
- **Dropped: `@node-rs/argon2`.** Password hashing uses `node:crypto` `argon2` (see the hashing policy above). That removes a single-maintainer native package and its 13 platform packages. What we write ourselves is salt generation, parameter storage in columns, rehash-on-login, and a `timingSafeEqual` check; none of it is cryptography.

## Consequences

- We own the session, MFA and API-key logic. That is the main risk, and it is why the primitives table and the NOT-built list are strict, and why every row in the ASVS table needs a test.
- Identity tables sit outside RLS. This is acceptable only because they hold identity, not tenant data, and ADR-0013 adds the allowlist test that makes it safe.
- Fast SHA-256 for API key secrets is correct only because the secrets are 256-bit random. Nothing a human chooses is ever hashed with it.
- Deferring OIDC and WebAuthn means M1 customers sign in with a password and TOTP only. The session model and `memberships` do not change when those arrive.
- Sessions in Postgres cost an indexed lookup per request. Revisit if the console load makes that visible.
